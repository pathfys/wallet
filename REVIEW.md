# PMR Wallet — ревью кода, аудит безопасности и что сделано

Объект ревью: `index.html` (2855 строк, Telegram Mini App: некастодиальный TON‑кошелёк GRAM/USDT + P2P).
Итог: сделан бэкенд, P2P по модели Bybit с блокировкой средств в смарт‑контракте эскроу, реальный чат,
админ‑панель на реальных данных; все демо‑данные удалены; закрыты найденные уязвимости.

## 1. Найденные проблемы в исходном коде

### Критические

| # | Проблема | Где | Последствия |
|---|----------|-----|-------------|
| C1 | «Блокировка» средств в P2P — это только запись в `localStorage` (`S.locks`). Монеты оставались на кошельке продавца. | `submitOffer`, `joinTradeGo`, `lockedFor` | Продавец получает фиат и выводит монеты через любой другой кошелёк (Tonkeeper и т. п.). Покупатель ничем не защищён — классическая P2P‑схема мошенничества. |
| C2 | Библиотеки, работающие с seed‑фразой и ключами (`@ton/crypto`, `@ton/ton`), грузились в рантайме с `esm.sh` / `jsdelivr` / `unpkg` без проверки целостности (SRI). | `importPkg`, `loadLibs` | Взлом или подмена любого из трёх CDN = кража seed‑фраз всех пользователей. |
| C3 | Роль администратора определялась на клиенте по `initDataUnsafe.user.id` (данные без проверки подписи) и автоматически на `localhost`. | `isAdminUser` | Любой мог открыть «Панель». Сами данные панели были фиктивными и локальными. |
| C4 | Демо‑данные выдавались за реальные: демо‑офферы, синтетическая статистика (`mulberry32`, `synthDaily`), фейковые автоответы «контрагента» в чате, фейковое число получателей рассылки, зашитый «реестр занятых ников», демо‑жалобы и баны. | `seedDemoOffers`, `seedAdminData`, `tradeSend`, `synthDaily` | Пользователь видит несуществующие сделки и «ответы» продавца; решения принимаются на основе выдуманных цифр. |
| C5 | Не было бэкенда: подпись Telegram `initData` нигде не проверялась (это признавал комментарий в коде). | весь P2P | Любой мог выдать себя за любого пользователя. |

### Высокие

| # | Проблема | Где | Исправление |
|---|----------|-----|-------------|
| H1 | Браузерная «биометрия» (WebAuthn‑ветка): пароль шифровался ключом из `"pmr-bio-" + navigator.userAgent` и лежал в `localStorage`; результат WebAuthn не проверялся криптографически. Фактически пароль хранился в открытом виде. | `bioSecret`, `bioEnroll` | Ветка удалена. Только Telegram `BiometricManager` (токен в Keychain/Keystore). Старые настройки при миграции отключаются. |
| H2 | Seed‑фраза при показе вставлялась в inline‑атрибут `onclick="…writeText('…seed…')"` — оставалась в DOM. | `revealSeed` | Обработчик через замыкание, фраза скрывается через 60 с, буфер обмена очищается. |
| H3 | Деньги считались во `float`: `toNano(String(amt - fee))` даёт `0.30000000000000004` → исключение или неверная сумма. | `sendTonOuts`, `sendWithFee`, `withdrawFee` | Вся арифметика в минимальных единицах `BigInt` (и на клиенте, и на сервере). |
| H4 | Все TON‑переводы с `bounce:false`, без проверки сети адреса. | `sendTonOuts` | Флаг bounce берётся из адреса (EQ/UQ), для неактивированного получателя — non‑bounceable (как в Tonkeeper); testnet‑адрес в mainnet отклоняется. |
| H5 | P2P‑комиссия удерживалась отдельной транзакцией клиента — легко обходилась. | `tradeComplete`, `releaseGo` | Комиссия зашита в смарт‑контракт эскроу и выплачивается им автоматически. |
| H6 | Нет защиты от перебора пароля; PBKDF2 160 000 итераций. | `doUnlock`, `deriveKey` | 600 000 итераций (OWASP), прозрачная миграция, растущая пауза после 5 ошибок (сохраняется между перезапусками), проверка сложности пароля. |
| H7 | Нет автоблокировки; мнемоника хранилась в памяти всю сессию. | `session.mnemonic` | В памяти только ключ; автоблокировка через 5 мин бездействия / 2 мин в фоне с обнулением ключа. |

### Средние и низкие

* Уникальность ника проверялась только локально; не было защиты от подмены похожими символами (латинская `a` vs кириллическая `а`, `admin` → `аdmin`). Теперь — на сервере, с «скелетом» ника, запретом смешения алфавитов и зарезервированных/служебных имён.
* Запасной QR отправлял адрес пользователя на `api.qrserver.com` (утечка приватности) — удалён.
* CSP почти пустая — теперь ограничены источники скриптов, стилей, соединений; `object-src 'none'`, `base-uri 'none'`, `frame-src 'none'`.
* Отправка USDT без учёта сети (USDT в testnet), «МАКС» во float — исправлено.
* Ошибки в `modalResult` и ссылках на обозреватель экранируются; внешние ссылки с `rel="noopener noreferrer"`.
* Опечатки логики: `send-max` для GRAM не учитывал газ корректно; история не ограничивалась по размеру — исправлено.

| # | Проблема | Риск | Исправление |

Проверено и в порядке: подпись `initData` (HMAC‑SHA256, `timingSafeEqual`, срок, отказ ботам); SQL — только
подготовленные выражения, динамические фрагменты — лишь константы и `?`‑плейсхолдеры, `LIKE` экранируется;
подпись каждого запроса + nonce + окно времени; лимиты на IP/пользователя/маршрут, таймауты, лимиты тела;
проверка участия в ордере для файлов и чата (IDOR); одноразовые тикеты WebSocket; админ‑маршруты только с ролью.

## 2. Новая архитектура

```
 Telegram (Mini App)                      Сервер (Node.js ≥22, без фреймворков)            Блокчейн TON
 ┌──────────────────────────┐   HTTPS    ┌──────────────────────────────────────┐   RPC   ┌───────────────────────┐
 │ index.html               │ ─────────► │ auth: initData HMAC + ключ устройства│ ──────► │ Эскроу‑контракт на     │
 │  • seed/ключи — только   │  подписан. │ P2P: объявления, ордера, таймауты,   │         │ каждую сделку          │
 │    на устройстве (AES)   │  запросы   │      апелляции, отзывы, статистика   │         │ (FunC, pmr_escrow.fc)  │
 │  • vendor/pmr-vendor.js  │ ◄───────── │ чат + фото (WebSocket, тикеты)       │         │  продавец → RELEASE    │
 │    (SRI, свой домен)     │   WSS      │ админка, рассылка, аудит‑лог          │         │  покупатель → CANCEL   │
 │  • сам строит и проверяет│            │ наблюдатель за эскроу, авто‑возвраты │         │  арбитр (подпись) →    │
 │    адрес эскроу          │ ──────────────────────────── транзакции кошелька ────────► │  RELEASE / REFUND      │
 └──────────────────────────┘            └──────────────────────────────────────┘         └───────────────────────┘
```

**Принцип:** платформа не хранит средства пользователей. Сервер хранит только объявления, ордера, чат и
зашифрованные реквизиты. Деньги сделки лежат в отдельном смарт‑контракте, который может отправить их
только покупателю (выпуск), обратно продавцу (возврат) или — комиссию — на фиксированный кошелёк сервиса.
У сервера нет «горячего» кошелька: решения арбитра — это подписанные внешние сообщения, газ платит сам контракт.

## 3. Безопасность: что и как защищено

### Повторное воспроизведение (replay)

| Канал | Защита |
|-------|--------|
| API‑запросы | При входе устройство создаёт **неэкспортируемый** ECDSA P‑256 ключ (WebCrypto). Каждый запрос подписан: `метод + путь + время + одноразовый nonce + SHA‑256 тела`. Сервер отклоняет запросы со временем вне ±60 с, повторный nonce (409), подменённое тело или неверную подпись. Украденный токен без ключа устройства бесполезен (есть тест). Использованные nonce хранятся **в SQLite**, поэтому перезапуск сервера не открывает окно для повтора перехваченного запроса. |
| Вход | Проверка HMAC‑подписи `initData` токеном бота (с `timingSafeEqual`), срок `auth_date` ≤ 24 ч, отказ ботам. `initData` **привязывается к ключу первого устройства**: скопированный `initData` (из логов, devtools Telegram Web, прокси) на другом устройстве даёт 401 `init_data_used` (тест). Ключ устройства — неэкспортируемый `CryptoKey` в IndexedDB, поэтому перезагрузка WebView не мешает повторному входу. |
| Создание ордеров/объявлений | Ключи идемпотентности (`idem`, UNIQUE в БД) — повтор не создаёт дубль. |
| Смена статусов | Оптимистичные переходы `UPDATE … WHERE status IN (…)` — двойное нажатие/гонка не выполнит действие дважды. |
| Привязка кошелька | Одноразовый challenge (5 мин) + подпись ключом кошелька; сообщение включает ID пользователя и адрес. |
| WebSocket | Одноразовый тикет на 30 с, полученный подписанным запросом. Токен не попадает в URL. |
| Переводы кошелька | `seqno` + `valid_until` (2 мин) в каждом сообщении WalletV4. |
| Решения арбитра в контракте | Подпись покрывает тег, **адрес конкретного контракта**, `seqno`, срок действия и действие. `seqno` хранится и растёт, поэтому повтор, подмена действия или подпись от другого эскроу отклоняются (тесты). |
| Оплата закрепления | Уникальный комментарий счёта + уникальный хеш транзакции. |

### DDoS и злоупотребления

* **nginx** (первая линия): `limit_req` на API и вход, `limit_conn`, таймауты заголовков/тела против slowloris, лимит размера тела. Для крупных атак — Cloudflare или аналог перед nginx.
* **Сервер**: токен‑бакеты на IP (600/мин — с учётом общих IP мобильных операторов) и на пользователя (240/мин), отдельные лимиты на вход, создание ордеров/объявлений, чат (20/мин, 5 за 5 с в ордер), загрузку файлов, апелляции, жалобы, рассылки; память ограничена (вытеснение старых ключей).
* HTTP: `headersTimeout`, `requestTimeout`, `keepAliveTimeout`, лимит заголовков, `maxConnections`, жёсткий лимит тела (32 КБ JSON, 3 МБ фото), отказ при `Content-Length` больше лимита до чтения тела.
* WebSocket: `maxPayload` 1 КБ, без сжатия (нет zip‑бомб), ≤3 соединения на пользователя, лимит частоты, ping/pong с отключением «мёртвых».
* Тяжёлые операции (RPC блокчейна) — только в фоновом наблюдателе пачками, с глобальным ограничением запросов в секунду и экспоненциальной паузой.
* Контракт: все проверки внешних сообщений выполняются **до** `accept_message()`, поэтому мусорные сообщения не тратят газ контракта (тест).
* Клиент: защита от параллельных обновлений баланса, экспоненциальные повторы, обновления на паузе, когда приложение скрыто.

### Только нативный Telegram (браузер, Telegram Web, F12)

* **Первый код страницы** — шлюз окружения. Приложение запускается, только если: есть `Telegram.WebApp` с подписанными
  `initData` (`hash`, `auth_date`), платформа не `web/weba/webk/webz/unknown`, страница не во iframe и есть нативный мост
  Telegram (`TelegramWebviewProxy` / `external.notify`). Иначе страница очищается до пустой, загрузка останавливается
  (`window.stop()`), модуль прерывается — ни одного обработчика, запроса или таймера. Обход для `localhost` удалён.
* **Сервер**: `index.html` отдаётся с `frame-ancestors 'none'` и `X-Frame-Options: DENY`, а запрос с `Sec-Fetch-Dest: iframe`
  получает 403 — Telegram Web показывает Mini App во iframe, поэтому там приложение не открывается даже при подделке
  клиента (тест).
* **F12 / devtools**: перехват F12, Ctrl/Cmd+Shift+I/J/C/K, Ctrl+U/S/P и контекстного меню (кроме полей ввода).
  Если отладчик всё же подключён (Telegram Desktop «Allow web view inspecting», отладка WebView на Android) —
  срабатывает детектор паузы `debugger`: ключ кошелька стирается из памяти, кошелёк блокируется, страница очищается.
* Честно: всё, что выполняется на устройстве пользователя, можно обойти (исходник страницы публичен, как у любого
  веб‑приложения). Поэтому безопасность не держится на этих барьерах: без валидной подписи Telegram сервер не даст
  сессию, а без ключа кошелька — средства не сдвинуть.

### Прочее

* **XSS**: всё, что приходит с сервера (ники, чат, условия, реквизиты), экранируется; CSP ограничивает источники скриптов и соединений, а встроенный скрипт приложения разрешён **по SHA‑256 хешу** (без `'unsafe-inline'`, хеш пересчитывает `build-vendor.mjs`) — внедрённый `<script>`/`onclick` не выполнится; изображения чата отдаются с `Content-Security-Policy: sandbox` и `nosniff`, показываются через `blob:`.
* **IDOR**: каждый маршрут ордера/файла проверяет участие пользователя (тесты: чужой ордер → 404).
* **SQL‑инъекции**: только подготовленные выражения.
* **Персональные данные**: реквизиты шифруются AES‑256‑GCM с привязкой (AAD) к владельцу; покупатель видит реквизиты только после блокировки средств; Telegram ID контрагентов не раскрываются пользователям; EXIF/GPS вырезаются из фото.
* **Загрузки**: только JPEG/PNG по сигнатуре, имена файлов случайные, файлы вне веб‑корня, `0600`.
* **Роли**: администраторы только из `ADMIN_IDS` на сервере (снятие из списка отзывает права при перезапуске); все действия админов пишутся в аудит‑лог; нельзя забанить админа.
* **Цепочка поставок**: в рантайме сервера две зависимости (`@ton/core`, `ws`), версии зафиксированы, `npm audit` — 0 уязвимостей. Фронтенд не грузит код с CDN.
* **Процесс**: systemd‑песочница (`ProtectSystem=strict`, `NoNewPrivileges`, без capabilities), отдельный пользователь, секреты в `.env` с правами 600, токены в логах маскируются.

## 4. P2P по модели Bybit

| Bybit P2P | Реализация |
|-----------|------------|
| Объявления (Buy/Sell), фиксированная и **плавающая** цена (% от рынка) | `side`, `priceType`, `floatPct` 80–120% от индекса CoinGecko (для RUB ПМР — курс `PRB_PER_USD`). |
| Общее количество, остаток, мин./макс. лимит в фиате | `total`/`available`, лимиты; эффективный максимум = min(лимит, остаток × цена). |
| Несколько способов оплаты, сохранённые реквизиты | Профиль «Способы оплаты»; реквизиты продавца копируются в ордер. |
| Время на оплату 15/30/60 мин | `payWindow` с таймером в ордере. |
| Условия объявления, требования к контрагенту | Текст условий, мин. число сделок и дней с регистрации. |
| Онлайн/офлайн, редактирование, удаление | Есть; нельзя удалить при активных ордерах. |
| Статусы ордера (коды API Bybit) | `5` ожидание блокировки в сети (как в некастодиальном Bybit Web3 P2P), `10` ожидает оплаты, `20` ожидает выпуска, `30` апелляция, `40` отменён, `50` завершён. |
| Заморозка монет продавца | Смарт‑контракт эскроу на сделку (средства у контракта, не у платформы). Плюс проверка реального баланса продавца в блокчейне при создании объявления, увеличении его объёма и перед каждым ордером: без монет (и GRAM на газ для USDT) ордер не создаётся, а объявление, по которому не хватает даже на минимальную сделку, скрывается с уведомлением продавцу. |
| «Я оплатил(а)» с подтверждением | Чекбокс‑подтверждение; ложная отметка — нарушение. |
| Выпуск с подтверждением паролем фондов | Подтверждение «деньги на счёте» + повторный ввод пароля/биометрия, транзакция RELEASE в контракт. |
| Автоотмена по таймауту оплаты | Отмена + автоматический возврат средств продавцу через решение арбитра. |
| Лимит отмен: 3 в сутки | Отмены после блокировки и таймауты оплаты считаются; при 3 за 24 ч покупки блокируются. |
| Апелляция через N минут после оплаты | `APPEAL_AFTER_MIN` (10), причины, описание, доказательства фото в чате; авто‑апелляция через 24 ч. |
| Поддержка в чате, решение спора | Сотрудник видит чат, пишет как «Поддержка», решает: выпуск покупателю / возврат продавцу / закрыть. |
| Чат ордера с изображениями | Текст + фото (JPEG/PNG), реальное время через WebSocket, уведомления ботом, если собеседник офлайн. |
| Отзывы и статистика мерчанта | 👍/👎 с комментарием; сделки за 30 дн., % выполнения, среднее время оплаты/выпуска, % положительных отзывов. |
| Комиссия | 2% с покупателя + 2% с продавца = 4% за ордер (настраивается `P2P_FEE_SIDE_BPS`), выплачивается контрактом. Клиент откажется от эскроу с комиссией выше `CONFIG.MAX_P2P_FEE_SIDE_BPS`. |
| Закрепление объявления (было «демо») | Реальная оплата on‑chain на кошелёк сервиса по счёту с уникальным комментарием, автоподтверждение. |

## 7. Что нужно сделать перед запуском

1. **Аудит смарт‑контракта у независимой компании до работы с реальными деньгами в mainnet.** Контракт
   небольшой и покрыт тестами, но для финансового продукта это обязательный шаг.
2. `cd server && npm run gen:keys` → `ARBITER_SECRET`, `DATA_KEY` в `.env`; публичный ключ арбитра
   вставить в `index.html` → `CONFIG.ARBITER_PUBKEY` (тогда клиенты откажутся от эскроу с чужим ключом).
3. Хранить `ARBITER_SECRET` как самый ценный секрет (офлайн‑копия, доступ только у сервера).
4. `BOT_TOKEN`, `ADMIN_IDS`, `TONCENTER_API_KEY`, `TG_APP_LINK`; при необходимости `PRB_PER_USD`.
5. Сначала прогнать всё на `TON_NETWORK=testnet` (TON‑сделки), затем mainnet.
6. nginx из `server/deploy/nginx.conf`, systemd из `server/deploy/pmr-wallet.service`, резервные копии
   `server/data/` (SQLite + фото), мониторинг логов (`journalctl -u pmr-wallet`).

## 8. Остаточные риски и ограничения (честно)

* **Доверие к арбитру** — как и на Bybit: при споре решение принимает поддержка. Ключ арбитра может
  направить средства конкретной сделки только её покупателю или продавцу, но не себе.
* Через `ESCROW_RECLAIM_DAYS` (14 дней) продавец может сам вернуть средства из незавершённого эскроу —
  страховка на случай остановки платформы. Апелляции нужно решать раньше (панель предупреждает).
* Сделки в USDT требуют у продавца ≈0.45 GRAM на газ (неиспользованное возвращается). Покупателю газ не нужен.
* Комиссия за вывод (2%) остаётся клиентской: некастодиальный кошелёк нельзя заставить платить вне приложения.
* Стили по‑прежнему требуют `'unsafe-inline'` в `style-src` (скрипты — уже по хешу).
* SQLite рассчитан на один экземпляр сервера (тысячи пользователей). Для горизонтального масштабирования —
  PostgreSQL + Redis для лимитов/nonce (логика уже изолирована в `db.js` и `security.js`).
